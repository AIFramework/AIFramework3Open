# Атлас

Атлас помогает языковой модели понять, есть ли в AIFramework готовая функция под задачу, прежде чем писать свою. Он работает как MCP-сервер: Claude Code или другой клиент запускает его и обращается к нему через стандартные потоки ввода и вывода.

Сейчас готовы индекс исходников, поиск по открытому API библиотеки, сборка стека под задачу, поиск дублей внутри библиотеки (в том числе исполнением) и сравнение с проектом, который построен на библиотеке.

## Индекс

```powershell
atlas index [папка] [--solution файл.sln]
atlas show <имя> [папка]
atlas package <сборка.dll> [папка]
```

`atlas index` открывает самое полное решение в корне репозитория (для AIFramework это `AIFramework.Full.sln`) и проект сниппетов туториалов `Tools/SnippetCheck`, если он есть. Каждый тип и метод, включая закрытые, становится единицей индекса. У единицы есть идентификатор в формате XML doc ID, сигнатура, XML-комментарий, тело, место в файле и имя функции AIScript, если метод ее реализует. Отдельно записывается, кто кого вызывает, и у каждого файла отмечена область: библиотека, тесты, туториалы, демо, утилиты.

Файл, текст которого не изменился, повторно не разбирается. Поэтому второй прогон упирается в загрузку проектов: на AIFramework это около 20–35 секунд против минуты с небольшим у первого.

`atlas show` печатает карточку единицы: сигнатуру, описание, кто ее вызывает по областям и что вызывает она сама. Здесь поиск идет по имени (`dsp.fft`, `Eigen.Symmetric(`), поиск по смыслу делает `atlas search`.

`atlas package` читает открытый API сборки так, как его увидит проект, подключивший библиотеку пакетом NuGet, и сравнивает состав с индексом исходников той же сборки. Код выхода 0 означает полное совпадение.

## Поиск

```powershell
atlas search <запрос> [--llm]
atlas embed [папка]
atlas eval [папка] [--sample N] [--misses файл]
```

Поиск идет по открытому API библиотеки (типы и методы с видимостью `public` из `src`) в несколько ступеней:

1. **BM25** по имени, имени функции AIScript и тексту `summary`, параметров и результата. Имена разбиваются по регистру (`CalcFFT` → «calc fft»), слова обоих языков сводятся к основе стеммером Портера. Реализация BM25 взята из `AI.NLP`, где для этого появился обратный индекс.
2. **BGE-M3** через OpenRouter: косинус между вектором запроса и векторами единиц. Векторы считает `atlas embed`, они хранятся в `%LOCALAPPDATA%\Atlas\vectors` по отпечатку текста, поэтому повторный запуск докупает только изменившееся.
3. **Слияние** выдач по рангам (Reciprocal Rank Fusion) и небольшая поправка в пользу методов, которые много где вызываются.
4. **Реранкер**, если задан `rerankModel`.
5. **LLM**, если задан `searchModel` и запрошен разбор (`--llm` или `explain` в MCP). Модель выбирает подходящие единицы, коротко объясняет выбор и пишет, чего для задачи не хватает. На кандидатов она ссылается только номерами из списка, поэтому выдумать несуществующий метод не может.

Сетевые ступени включаются сами, когда есть ключ и модель. Без них работает BM25.

`atlas eval` меряет поиск на эталоне, собранном из самого репозитория. В туториалах запросом служит раздел «Постановка задачи», ответом типы из раздела «API». В демо запрос составлен из названия и подзаголовка алгоритма, ответ берется из `ApiClass`. Вопросы, в тексте которых уже есть имя ответа, дополнительно считаются отдельно (строка «без имени»), чтобы совпадение слов не выдавалось за поиск по смыслу. `--sample N` прореживает эталон для дорогих прогонов с LLM.

## Сборка стека

```powershell
atlas stack <задача> [--steps "шаг; шаг"] [--script] [--candidates]
atlas path <тип> <тип>
atlas stack-eval [--script]
```

`atlas stack` отвечает на вопрос «из каких функций библиотеки собрать задачу». Шаги можно передать через `--steps`. Если их нет, задачу разбивает модель из `searchModel` через планировщик `AI.LLM`, а без ключа Атлас режет текст по переносам строк, точкам с запятой и связкам «затем», «потом».

Для каждого шага поиск дает кандидатов, а лучевой поиск выбирает цепочку по трем признакам:

- насколько кандидат подходит шагу;
- стыкуется ли выход предыдущего шага со входом этого: тот же тип или его предок, либо одно преобразование (оператор приведения, конструктор, метод `To…`);
- как часто в реальном коде результат одного метода идет во вход другого. Эту статистику индекс собирает по тестам, туториалам, демо и самой библиотеке.

Если лучший кандидат покрывает меньше 45% значимых слов шага, шаг объявляется пробелом: в библиотеке этого нет, писать свое. Натянутый метод опаснее пробела. `--candidates` показывает кандидатов каждого шага с покрытием, чтобы было видно, почему шаг стал пробелом.

Лучший стек проверяется без запуска. Для C# из шагов строится каркас «результат шага идет во вход следующего» и компилируется Roslyn против собранных сборок. С `--script` стек ищется только среди функций AIScript и проверяется так же, как скрипт перед запуском. В отчете есть проекты, которые придется подключить, их пакеты и нативные части.

`atlas path` показывает до трех кратчайших цепочек методов от типа к типу, например `atlas path Vector Peak`.

`atlas stack-eval` собирает стеки для десяти задач бенчмарка AIScript и считает, на скольких шагах функция выбрана верно. Эталон взят из решений этих задач в `BenchmarkTests`.

## Дубли

```powershell
atlas dups [--limit N] [--behavior]
atlas dup-check <файл|-> [--intent "замысел"]
atlas dup-explain <a> <b>
atlas dup-decide <a> <b> <вердикт> [причина]
atlas dup-eval
```

Детектор сравнивает методы библиотеки с телами (закрытые тоже) по нескольким признакам:

- **код**: тело разбирается Roslyn, имена переменных заменяются на `ID`, числа на `NUM`, строки на `STR`; из токенов строятся шинглы по пять, а MinHash с LSH из `AI.NLP` находит пары с похожими шинглами без перебора всех пар. Переименованная копия дает совпадение 1,0;
- **описание, имя, вызовы**: доля общих слов XML-комментария, одинаковое простое имя в разных типах, общие вызываемые методы;
- **константы и управление**: общие «магические» числа (кроме 0, 1, 2) и одинаковое число циклов, ветвлений, возвратов;
- **входы**: те же типы данных на входе и на выходе.

Вердикт выносится по порогам, подобранным на эталоне и выборке находок:

| Вердикт | Когда | Что делать |
|---|---|---|
| копия | код совпадает на 80% и больше | заменить вызовом канонической версии |
| похожий код | код от 60%, совпадает имя или описание | проверить, не одна ли это функция |
| один предмет, разный код | функции с тем же именем или описанием и теми же входами | проверить исполнением: дубль, расхождение или сознательное перекрытие |
| копия в перегрузках | копия внутри одного типа | вынести общую часть |

Каноническая версия выбирается по слою проекта (ближе к ядру лучше), затем по числу мест вызова. Обертка, которая вызывает другой метод, дублем не считается. Переопределения одного базового метода сравниваются только как копии, а конструкторы из одних присваиваний и тела-тексты (справка, шаблоны) не считаются доказательством по коду.

`atlas dup-check` проверяет черновик до того, как он попадет в библиотеку: код метода или только тело, и по желанию замысел словами. По замыслу дополнительно работает поиск, отфильтрованный тем же порогом покрытия слов, что и шаги стека.

`atlas dup-explain` разбирает пару: признаки, вердикт, решение журнала и начала обоих тел. Если заданы ключ и `verdictModel`, для серой зоны («похожий код», «один предмет, разный код») модель получает оба тела с признаками и отвечает одним словом из списка: дубль, расхождение, перекрытие, нет связи.

Решения человека хранятся в журнале `%LOCALAPPDATA%\Atlas\<имя репозитория>-<хеш пути>\decisions.json`, а не в репозитории. Решенная пара пропадает из отчета, пока тело одного из методов не изменится: тогда решение переоткрывается. В журнал заранее записаны три сознательных перекрытия из `Econometrics.md`: `StateSpace` и `KalmanFilter`, два `Cholesky`, `Ols` и `MultipleRegression`.

`atlas dup-eval` меряет детектор на эталоне из семи подтвержденных дублей и четырех пар, похожих по имени, но разных по смыслу.

### Исполнение

Сходство кода и имен не говорит, считают ли методы одно и то же. Поэтому `dup-explain` и `dups --behavior` исполняют оба метода на одних и тех же входах и сравнивают выходы:

- **входы** строятся по сигнатуре с сидом: сначала крайние случаи (пустой ряд, одно значение, константа, NaN, огромные и малые величины), затем случайные, половина из них положительные. Все ряды одного вызова одной длины, таблицы квадратные той же стороны;
- **переходник** передает аргументы первого метода второму: перестановки, `Vector` и `double[]`, `Matrix` и `double[,]`, значения по умолчанию. Метод, который меняет массив на месте, сравнивается по массиву после вызова;
- **связь выходов** ищется на обычных входах: равны (допуск 1e-6), знак, постоянный множитель, множитель от длины n (n/(n−1) у дисперсии со смещением и без), сдвиг, нормировка рядов. Сравнение с допуском для `Vector`, `Matrix` и `ComplexVector` лежит в ядре: `AlgebraicStructsExtensions.ApproxEquals`.

| Итог | Что значит |
|---|---|
| поведенческий дубль | выходы равны на всех входах |
| дубль, кроме крайних случаев | равны на обычных входах, крайние расходятся; строки таблицы показывают где |
| дубль с поправкой | одно имя или описание, выходы связаны преобразованием, например множителем (n−1)/n |
| расхождение | одно имя или описание, но на обычных входах выходы разные: один из методов, возможно, неверен |
| связанные функции, разные функции | имена разные, выходы связаны или различаются: это функции одного шаблона (Ln и Log10, Acos и Tanh), а не дубли |
| не проверено | методы не принимают сгенерированные входы, аргументы не сопоставить, процесс снят |

Внутри одного типа «одно и то же» означает одно имя: описания там пишутся по шаблону. Разные константы у методов без аргументов (`ModelName` в разных классах) расхождением не считаются. Для методов во `float` допуск 1e-4. Если оба метода вызывают один помощник библиотеки, отчет предупреждает: совпадение выходов не доказывает, что верны оба.

Итоги хранятся в `%LOCALAPPDATA%\Atlas\<имя репозитория>-<хеш пути>\behavior.json` по отпечаткам тел и времени сборки: пара исполняется заново, только если изменился ее код или сборка. В MCP `dup_report` с `behavior` тратит на новые пары не больше минуты, остальные досчитываются при следующем вызове.

Методы исполняются в отдельном процессе `atlas worker`. Хозяин снимает его, если пара считается дольше 20 секунд или процесс занял больше 1 ГБ, и поднимает заново при следующей паре. Процесс запускается в пустой временной папке и без переменных окружения с KEY, TOKEN, SECRET или PASSWORD в имени. Исполняются только статические и закрытые методы над данными: параметры и результат из чисел, рядов (в том числе целых), таблиц, строк. Открытый экземплярный метод зависит от состояния объекта и не исполняется. Имена вроде `Save`, `Load`, `Send`, `Plot` и проекты графики, LLM и GPU не исполняются, а их сборки даже не загружаются.

## Проект на библиотеке

```powershell
atlas project [папка] [--limit N] [--behavior]
```

Если репозиторий подключает AIFramework, Атлас работает в режиме проекта. Связь ищется по `.csproj`: ссылка на проект `AI` или `AI.*` вне репозитория (свойства вида `$(AiFrameworkCore)` подставляются) или пакет с таким именем. `.slnx` поддерживается наравне с `.sln`.

- **Снимок библиотеки.** Для исходников это собственный индекс репозитория библиотеки, помеченный состоянием git: коммит и отпечаток незакоммиченных правок (без `bin` и `obj`). Если состояние то же, библиотека не переиндексируется, сколько бы проектов на нее ни смотрело. Для пакетов снимок строится по DLL из кэша NuGet в `%LOCALAPPDATA%\Atlas\lib\<версия>`: тел там нет, сравниваются имена и описания открытого API.
- **Индекс проекта** лежит отдельно и строится поверх снимка. Поиск и стеки идут по библиотеке, дубли — по библиотеке и проекту вместе.
- **Отчет** делит находки на три направления, и у каждой сказано, где править:
  1. *проект повторяет библиотеку*: заменить вызовом открытого метода библиотеки. Если сборка проекта не ссылается на библиотеку, отчет предупреждает, что понадобится ссылка. Одной похожей формы короткого кода мало: нужно одно имя, одно описание или почти тот же код;
  2. *дубли внутри проекта*: свести к одной версии, каноническая берется из нижнего слоя проекта;
  3. *общий код проекта*: статические синхронные методы над простыми данными (числа, строки, коллекции, типы библиотеки), которые не трогают файлы, сеть, процессы и базы и не зовут код проекта. Для каждого поиск по библиотеке говорит, нет ли там уже похожего, и где его разместить.

`dup_check` в проекте ищет по замыслу и в библиотеке, и в коде проекта, `dup_explain` и `dup_decide` находят методы в обоих индексах, журнал решений проекта лежит рядом с его индексом.

### Что уходит в OpenRouter

Код библиотеки публичный, код проекта может быть закрытым. Для каждого проекта это задается в `settings.json`:

```jsonc
{
  "projects": {
    "KnowledgeGraph": "names",          // имя папки или полный путь к репозиторию
    "C:\\Work\\Secret": "none"
  }
}
```

`none` (по умолчанию, пока не задано): модель код проекта не видит, BM25, MinHash и исполнение работают локально, вердикт модели по паре с кодом проекта не запрашивается. `names`: уходят сигнатуры и описания, тела нет. `all`: уходит все. Каждый запрос к модели с кодом дописывается в `%LOCALAPPDATA%\Atlas\outbound.jsonl`, так что отправленное можно проверить без сети. Векторы BGE-M3 считаются только для открытого API библиотеки.

## Инструменты сервера

| Инструмент | Что делает |
|---|---|
| `script_help` | Справка по AIScript: задачи, пространства имен, сигнатуры, поиск по словам задачи |
| `check_script` | Проверяет скрипт AIScript без исполнения: имена, аргументы, типы |
| `run_script` | Исполняет скрипт с профилем `Untrusted`, то есть без сети и без записи файлов |
| `api_search` | Ищет в библиотеке типы и методы под задачу, описанную словами; `explain` включает разбор моделью |
| `api_describe` | Карточка типа или метода: сигнатура, описание, кто вызывает, что вызывает он сам, откуда приходит вход и куда уходит результат |
| `find_stack` | Стек под задачу из нескольких шагов: методы по порядку, связи между шагами, пробелы, проверка компиляцией или скриптом |
| `dup_check` | Есть ли в библиотеке то, что собираешься написать: по коду черновика и по замыслу |
| `dup_explain` | Разбор пары методов: признаки, вердикт, каноническая версия, решение журнала, вердикт модели |
| `dup_report` | Дубли в библиотеке без уже решенных пар |
| `dup_decide` | Записывает решение по паре в журнал; вызывать только по решению человека |
| `atlas_status` | Показывает, задан ли ключ OpenRouter и какие ступени поиска включены |

## Сборка и подключение

Сервер публикуется в кэш пользователя, а не запускается из `bin` репозитория: Claude Code держит запущенный сервер открытым, и сборка в репозитории упиралась бы в занятый файл.

```powershell
dotnet publish Tools/Atlas -c Release -o "$env:LOCALAPPDATA\Atlas\server"
claude mcp add --scope user atlas -- <путь к опубликованному серверу>/atlas.exe
```

Ключ `--scope user` записывает подключение в настройки пользователя, поэтому сервер доступен в любом проекте, а в репозиторий ничего не попадает. Корень проекта сервер берет из `CLAUDE_PROJECT_DIR`, а без нее из текущей папки.

Опубликованный сервер находит свои папки по месту установки: кэш — это папка над `server`, настройки — `Roaming\Atlas` рядом с ее `Local\Atlas`. Переменные `ATLAS_CACHE` и `ATLAS_CONFIG` перекрывают это правило. Если приложение Claude установлено пакетом MSIX (см. «Аудит»), регистрировать сервер и хук нужно по физическому пути в папке пакета, например `C:/Users/<пользователь>/AppData/Local/Packages/Claude_<id>/LocalCache/Local/Atlas/server/atlas.exe`. Тогда один и тот же exe работает с одними данными и в приложении, и в Планировщике, и в обычном терминале. Инструкция сервера говорит модели порядок работы: `api_search` до своего кода, `find_stack` для задач из нескольких шагов, `dup_check` перед новым методом и что делать с замечанием хука.

## Циклы

### Хук после правки

```jsonc
// .claude/settings.local.json (исключен из git) или настройки пользователя
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write|MultiEdit",
        "hooks": [ { "type": "command", "command": "<путь к опубликованному серверу>/atlas.exe hook", "timeout": 30 } ]
      }
    ]
  }
}
```

`atlas hook` читает событие Claude Code со стандартного ввода. Новые и измененные методы правленного `.cs` сравниваются с индексом, каким он был до правки. Если похожее уже есть, в том же ходе модель получает замечание «Атлас после правки» со ссылкой на существующий метод. Это быстрый путь: без модели, без исполнения, без переиндексации, около двух секунд. Формы тел берутся из кэша `shapes.bin` рядом с индексом библиотеки. Методы, тело которых не изменилось, не проверяются, поэтому старые находки при каждой правке не повторяются. Хук молчит, если индекса нет, файл не C# или это тест; ошибки пишутся в `%LOCALAPPDATA%\Atlas\hook.log`, а не в работу модели.

### Аудит

```powershell
atlas audit [папка] [--build]
```

Цикл гигиены. По желанию собирается решение, затем обновляются индексы (библиотека — только при новом состоянии git), ищутся дубли, пары исполняются (из кэша). Результат сверяется с журналом решений и прошлым аудитом. Отчет показывает только перемены: новые находки, новые расхождения, переоткрытые решения и исчезнувшие пары. Если оба метода исчезнувшей пары живы, это обычно слияние (один стал вызывать другой), и исполнение проверяет, что выходы остались прежними. Повторный прогон без изменений дает «Изменений с прошлого аудита нет». Отчет пишется в файл `audit-<дата>.md` рядом с индексом.

Ежедневный запуск делает задача Планировщика Windows «Atlas daily audit» (10:00, а если компьютер был выключен, то при первой возможности). Она запускает сценарий `audit-daily.ps1` для AIFramework3Open и KnowledgeGraph и дописывает отчеты в `audit-daily.log` в папке кэша.

Приложение Claude для Windows упаковано как MSIX, и `%LOCALAPPDATA%` и `%APPDATA%` его процессов виртуализированы: то, что сессии Claude пишут в `%LOCALAPPDATA%\Atlas`, физически лежит в `%LOCALAPPDATA%\Packages\Claude_<id>\LocalCache\Local\Atlas`. Процесс вне приложения (Планировщик, обычный терминал) видит реальную AppData. Поэтому сценарий запускает сервер по физическому пути пакета, а тот берет кэш по своему месту: ежедневный аудит работает с теми же индексами, кэшами и историей аудитов, что и сессии Claude.

### Калибровка

```powershell
atlas calibrate [папка]
```

Логистическая регрессия из AI.Econometrics учится предсказывать «то же поведение» по признакам пары. Метки берутся из журнала решений (решение человека важнее) и из исполнения. Треть пар откладывается для замера: на библиотеке модель верна в 86% случаев, правило «копия — дубль» в 34%, ответ большинства в 58%. Веса лежат в `%LOCALAPPDATA%\Atlas\calibration.json`, и отчеты показывают вероятность того же поведения у каждой пары, в том числе у тех, что исполнить нельзя.

Методы, чью карточку модель открыла после поиска (`api_describe`), попадают в журнал `selections.json` и поднимаются в выдаче `api_search`.

## Ключ OpenRouter

Репозиторий публичный, и ключ, попавший в историю git, приходится считать утекшим. Поэтому Атлас читает ключ только из переменной окружения `OPENROUTER_API_KEY`:

```powershell
[Environment]::SetEnvironmentVariable("OPENROUTER_API_KEY", "<ключ>", "User")
```

Перезапускать Claude Code после смены ключа не нужно: если в окружении процесса переменной нет, Атлас читает ее из переменных пользователя. Без ключа сервер тоже работает, но векторизатор, реранкер и LLM выключены, о чем сообщает `atlas_status`.

## Настройки

Модели задаются в `%APPDATA%\Atlas\settings.json`. Файл необязателен, и если его нет, действуют значения по умолчанию:

```jsonc
{
  "embeddingModel": "baai/bge-m3",   // векторизатор, по умолчанию BGE-M3
  "rerankModel": null,               // реранкер, например "cohere/rerank-v3.5"; null выключает ступень
  "searchModel": null,               // LLM поиска и разбиения задачи на шаги (быстрая модель)
  "verdictModel": null               // LLM вердиктов по дублям (сильная модель)
}
```

Поле с ключом в этом файле игнорируется намеренно: ключ живет только в переменной окружения.

Индекс лежит в `%LOCALAPPDATA%\Atlas\<имя репозитория>-<хеш пути>\index.db`. Это кэш, его можно удалить в любой момент, и Атлас построит индекс заново.

## Сторож секретов

```powershell
atlas guard [папка]
```

Команда просматривает файлы рабочего дерева git: отслеживаемые и новые, если они не исключены `.gitignore`. Она ищет ключи формата OpenRouter (`sk-or-v1-` и 64 шестнадцатеричных знака) и точное значение `OPENROUTER_API_KEY`. В отчет попадают только файл и строка, само значение не выводится. Код выхода 0 означает, что ключей нет, 1 означает находку, 2 означает ошибку, например папка не в репозитории git.

Команда `atlas status` печатает то же, что инструмент `atlas_status`.
